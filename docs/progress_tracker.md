**Rule**: Track only what is actionable now. The active sections are:
- **Blocking Issues** — must-fix items before merging the current branch and cutting a release. Items move out of here once resolved (into [`completed_milestones.md`](completed_milestones.md)).

## Open Non-Blocking Issues

| Issue | File | Notes |
|-------|------|-------|
| Contabilidad: a closed quarter's figures change after AEAT cancellation or rectification | `src/app/cancelinvoicedialog.cpp`, `src/app/rectifyinvoicedialog.cpp`, `src/contabilidad/contabilidad.cpp` | From the 2026-10-08 Contabilidad data-flow review. Most important of this batch. Neither dialog checks the accounting lock. Cancelling at AEAT sets `verifactu_estado = ANULADA` on rows that keep their original `fecha_pago`, and a substitution rectification marks the originals `RECTIFICADA`, so the garment silently drops out of its **original** quarter even when that quarter is closed (`edit_lock = 1`). Regenerating the closed quarter (Trimestral on a locked quarter re-runs the report from current data) then gives different figures from the report that was filed. Fiscally, a cancellation or rectification after filing is normally regularised in the period where it happens, not the original one. Decide the rule with the gestoría, e.g. count the negative in the cancellation/rectification period, or freeze closed quarters' figures and report later changes separately. |
| Contabilidad: rectificativa rows are inserted unlocked into a locked month | `src/app/rectifyinvoicedialog.cpp` (insert, `edit_lock = '0'`) | From the 2026-10-08 review. The new rectificativa row takes `fecha_pago` = the chosen invoice date and `edit_lock = 0`, with no check that the month is open. It then adds income to a closed quarter and stays editable there. Related to the cancellation/rectification row above: decide the target period, then either block dates in locked months or insert with the month's lock state. |

| Full app translation (English) | `src/**` (all `tr()` sites), `resources/i18n/` | The `app.language` setting currently only localizes **Qt's built-in** strings (standard dialogs) via the bundled `qtbase_es.qm`. The app's own UI strings are Spanish literals, so `en` gives English standard dialogs + Spanish app text. A full English option needs the app's `tr()` strings extracted with `lupdate` into a `laideal_en.ts`, translated, compiled to `laideal_en.qm`, bundled as a resource, and loaded in `main.cpp` alongside the Qt catalog. Large, mostly-mechanical i18n pass; do only if an English deployment is actually needed. |

(b) Per-row Base/IVA cells are rounded to cents while the total row uses the unrounded sum, so a hand-summed column can be a few cents off the printed total (standard presentation, but could add a note). Make both paths treat it the same way (ideally reject it on write). |
